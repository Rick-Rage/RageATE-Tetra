; This version of my DS90UB926Q chip initialization file performs the minimal steps
; necessary at power-up. Note that after we test this chip's registers (which involves
; writing arbitrary values into them) the initialization shown in this minimal version
; will NOT be sufficient to bring the chip back into normal operation. Hence after
; a test regiment you will need to use the "full" version of this initialization file.

; A semi-colon indicates a comment line.
; The format of the non-comment lines is:
; RegName  RegValue
; A RegValue can be expressed in hex if preceded by 0x or 0X.
; For those registers that consist of separate bit fields the subsequent comment lines describe:
;   LSBit   NumBits  Unsigned/Signed  FieldName  Explanation
; The read-only registers (such as ?, etc.) are identified in comment lines.

;SlaveID0             0x00
;  1  7  Unsigned  SlaveDevice0ID         I2C address of the remote slave device 0 attached to the remote serializer
;  0  1  Unsigned  Reserved               this bit is reserved
; We don't need to initialize this register because our desired value is already the chirp's power-on default value.

; In order to cause the 926 to convince an attached 925 to act as an I2C proxy
; for an I2C transaction originating on the 926 side but targeting an
; I2C slave on the 925 side (other than the 925 itself) you MUST employ one pair
; of the 926's SlaveIDx and SlaveAliasx registers. For example, assume the remote
; 925 has the default 7-bit slave dev address 0x0C (which TI's literature often
; writes as the 8-bit address 0x18). Furthermore, assume that you need to cause
; this remote 925 to communicate with (i.e. proxy I2C transactions with an I2C
; device having the 7-bit slave dev address 0x02 (which is the 8-bit addr 0x04).
; To accomplish this you must initialize the 926's SlaveID0 reg with the 8-bit
; address 0x04. This SlaveID0 reg holds the I2C address that will ultimately be
; employed on the remote end of the FPD-Link III cable for "proxied" transactions.
; Furthermore you must initialize the 926's SlaveAlias0  reg with an arbitrary
; (8-bit) address X not already claimed on the local bus. It is acceptable to use
; the same value as was just put in the SlaveID0 register.
; You then initiate a transaction on the 926's SCL/SDA pins that targets the
; address X held in the SlaveAlias0 register. This will cause the 926 to cause
; the 925 to recreate this same transaction on the far side of the cable but
; with the remapped I2C slave dev address taken from the value in the 926's
; SlaveID0 reg (i.e. 0x02).

; This need to employ the SlaveAlias register is explained in TI document
; SNLA222 entitled "I2C Over DS90UB913/4 FPD-Link III With Bidirectional
; Control Channel". Furthermore the 926's Configuration1 reg (at offset addr 3)
; must have the "I2C Pass Thru" bit set. [There is also an I2C "Pass Thru All" bit
; in the I2cControl1 reg at offset addr 5 but you don't want that -- see TI SNLA222.]

; Note that you don't need to employ the 926 (or 925) SlaveIDx and SlaveAliasx
; registers in order to convince the local 926 to communicate with the remote 925
; (but you DO NEED to set the I2cPassThruMode bit in the local 926's Configuration1
; reg in order to communicate with the remote 925).
